"The rules say yes. The form says no." Local-first software consistency verifier.

1. Overview & Core Architecture

RuleGap detects and proves discrepancies where a published eligibility rule permits an applicant, but an online application form actively rejects them. It is built as a local-first developer instrument with three primary architectural components:

  • Contract & Boundary Generator: Ingests policy guidelines or PDFs and extracts a deterministic rule contract (e.g., income <= 300000 INR). Deterministically derives exact boundary points (299999, 300000, 300001) and demonstration probes.
  • Black-Box Browser Runner: Spawns hermetic Chromium instances via Playwright under route-restricted network isolation, submitting test values into the actual form DOM and capturing explicit feedback messages and viewport screenshots.
  • Evidentiary Workbench & Export: Provides a dense Workshop Gridline UI with 4-state summary metrics, synchronized run history, deep screenshot inspection drawer, and a self-contained offline HTML report generator with base64-embedded screenshots.

2. Three-Stop Code Route

Follow a single verification action from rule derivation to browser assertion and offline export:

Stop 1: Rule Engine & Boundary Derivation

src/shared/ruleEngine.ts -> generateBoundaryTestCases

Generates exact boundary probe integers around the rule threshold according to the relational operator (e.g., for income <= 300,000 INR: threshold - 1 [299,999] evaluates to ACCEPT, threshold [300,000] evaluates to ACCEPT, and threshold + 1 [300,001] evaluates to REJECT). This ensures test generation is deterministic and mathematically calibrated to the operator before any browser interaction begins.

Stop 2: Independent Black-Box Form Observer

src/server/runner/formObserver.ts -> observeFormSubmission

Navigates a fresh, hermetic Playwright page context to the target form, enters the test probe value, clicks submit, and extracts the resulting DOM state without reading any client validation logic. It records whether the form accepted the input, rejected it with specific error text, or yielded an inconclusive state, and captures a timestamped viewport screenshot.

Stop 3: Discrepancy Classification & Offline Evidence Export

src/server/report/reportGenerator.ts -> generateHtmlEvidenceReport

Binds the expected policy outcome against the observed form response. If the policy says ACCEPT but the form yields REJECTED, it marks a CONFIRMED_MISMATCH. It packages the entire run into a self-contained, single-file HTML report with embedded base64 screenshots and discrete sampling disclaimers.

3. "To Change This, Start Here" Extension Pointers

Compound Rules & Multiple Fields
src/shared/contract.ts & ruleEngine.ts

Extend schemas to model multi-field compound requirements (e.g., household income cap combined with minimum GPA) and multi-variable combinatorial boundary generation.

Additional Authorized Form Adapters
src/server/routes/fixtures.ts & formObserver.ts

Add new local or staging fixture adapters with custom field selectors, submit actions, and domain-specific feedback containers.

Non-Numeric & Categorical Constraints
src/shared/contract.ts & ruleEngine.ts

Introduce categorical qualification rules (e.g. state residency, enrollment status) with discrete equivalence partitioning alongside numeric boundaries.

CI / Automated Regression Pipeline
src/tests/ & package.json

Package the headless Playwright runner as a command-line CI verification step that fails pull requests when web forms drift from policy contracts.

4. A Practice to Reuse: Four-State Classification Invariants

Decoupling Policy Expectations from Form Observations

A common pitfall in automated compliance testing is treating any form failure as a rule discrepancy. If a form fails to submit due to a network glitch, missing DOM selector, or unrelated required field, classifying that as a "Policy Bug" produces false alarms and erodes developer trust.

The Reusable Pattern: Model your verification engine with explicit four-state classification: compare independent Policy Expectation (ACCEPT | REJECT) against the Observed Form Outcome (ACCEPTED | REJECTED | INCONCLUSIVE):
• Consistent: Observable form behavior matches policy expectation (ACCEPT matches ACCEPTED, or REJECT matches REJECTED).
• Confirmed Mismatch: Form rejects an eligible applicant (ACCEPT vs REJECTED) or accepts an ineligible applicant (REJECT vs ACCEPTED).
• Inconclusive: Form exhibits ambiguous feedback or unrelated field failures.
• Execution Error: Target selector or submission element is unfindable in the DOM.

5. Running RuleGap Locally

RuleGap is fully self-contained and runs with zero external SaaS dependencies or paid API keys:

# Build client and server bundles
npm run build

# Start local server on 127.0.0.1:3000
npm start

# Run complete verification test suite
npm test
